# ICMR-STW AI: Security, Privacy & Clinical Safety Architecture

## 1. Clinical Grounding & Decision-Support Safety

The ICMR-STW AI is explicitly designed as a **clinical decision-support and educational system**. It does **NOT** function as an autonomous medical practitioner.

### 1.1 Strict Grounding Directives
1. **ICMR Authoritative Source Primacy**: The system draws strictly from official ICMR Standard Treatment Workflows.
2. **Deterministic Citation Tracing**: Every recommendation or workflow sequence generated by the AI must cite:
   - STW Document Title
   - Volume and Edition
   - Exact Page Number
   - Verifiable excerpt from retrieved chunks
3. **Safe Refusal (Anti-Hallucination)**: If retrieved chunks do not exceed relevance thresholds or do not contain conclusive ICMR guidance for a specific inquiry, the system explicitly returns:
   *"Insufficient ICMR evidence was retrieved to answer this safely."*

---

## 2. Protected Health Information (PHI) & Privacy Controls

Even though ICMR STW AI is designed for guideline discovery and workflow navigation, clinicians may input clinical case snippets:
1. **Client-side & Gateway Sanitization**: Automated masking of phone numbers, email addresses, and national identifiers (`mask_sensitive_phi`).
2. **Ephemeral Inference**: Patient-specific context strings are never stored into training pools or vector embeddings.
3. **Zero Secret Exposure**: All API keys (OpenAI, Groq, local endpoints) are strictly managed via environment variables and excluded from git tracking.

---

## 3. Network & Application Hardening

- **CORS Safeguards**: Strict whitelist of origins (`http://localhost:3000`, production frontend domains).
- **HTTP Security Headers**:
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
  - `X-Clinical-Safety: ICMR-Evidence-Grounded-Only`
- **Rate Limiting & Input Bounds**: Query strings are bounded by character and token thresholds (`MAX_QUERY_LENGTH = 500`) to prevent prompt injection and denial-of-service vectors.
